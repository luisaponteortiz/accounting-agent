# Implementation decisions

- **D-001 — Product scope (November 14, 2026):** General Accounting Agent OS for the full accounting cycle. Bird Bowl is a client implementation; card preparation is the first test workflow. The user's correction supersedes any card-only product framing. No unrelated SS business-development agents.
- **D-002 — Local execution stack:** Python standard library, SQLite, static HTML/JS for this executable slice. Observed Python 3.9.6; Node, Docker, uv and proposed Python libraries unavailable. Avoid a dependency-installation prerequisite while producing testable software. Material deviation from default stack is explicit; no PostgreSQL/production claims. M0–M5 as a whole are not complete.
- **D-003 — Modules:** generic workflow runner and capability registry first; demonstrate card preparation, journal validation and close readiness. AP/AR/reconciliations/reporting/analysis remain explicit deferred modules.
- **D-004 — Client facts:** unconfigured real Bird Bowl profile and a distinct fictional demo profile. No actual chart/mappings/receipt policies asserted. Demo policy may authorize internal synthetic preparation only.
- **D-005 — Conservative review:** immutable artifacts, separate independent human demo decisions, current-generation checks; any client input/config revision invalidates prior approvals. Review only authorizes reviewed preparation export, never posting or close.
- **D-006 — Autonomy:** scoped synthetic mandates, deduplicated simulated recurring events and durable background worker. No live schedules, credentials, network/model calls, deployments or ledger writes.

- **B1/T-03 — Review independence:** Trusted Actor records now distinguish human/service. Hashed artifact contributors include the enqueue actor, committing worker, mandate issuer, scoped input suppliers and profile registrant. All review decisions require a non-contributing human reviewer; actor-name prefixes grant or deny nothing. Old artifacts lacking contributor provenance fail closed for new decisions. Synthetic mandates require a human preparer; independent mandate/policy activation remains Batch 2, not implied by this change.
- **B1/T-04 — Occurrences versus runs:** Schema migration 2 moves recurrence uniqueness to durable occurrences, links attempts, and adds a database unique partial index permitting one completed run per occurrence. Stale held attempts can be re-dispatched; unfit mandates are held independently without rolling back other work or the clock. Missed slots are explicit skipped_no_catch_up records. Synthetic windows are bounded to 10,000 slots to bound skip recording. Existing immutable evidence/artifacts/decisions/audit are never rewritten.
- **B1/T-05 — Durable accounting periods:** Migration 3 adds period records/history, immutable source-period bindings and frozen run references. Human independent reviewer operations open/lock/reopen periods; locks do not change knowledge generation or reviewed work. Dated inputs are assigned by their explicit fixture date; sources without a configured period are quarantined as UNASSIGNED_ACCOUNTING_PERIOD, not prepared under another month. Undated documents require explicit packet period or exactly one configured period. Late locked-period evidence is retained but not admitted until an audited reopen.
- **B1/T-05 deliberate test/API changes:** The original period field was removed from profiles. Seed/reviewer harnesses now open periods explicitly; FV-J07 verifies locked dispatch refusal via lock_period; FV-J05 verifies quarantine rather than wrong-period preparation. Original teaching TX-008 is now a source-period exception until October opens, so the initial artifact count changes 21→20 (12→11 card items). Original wrong-period journal/derived V-10 tests assert own-period validation/quarantine. No blocker was weakened and no source was discarded. Original supplied scripts remain under review/original/; exports/FABLE_REVIEW_RESPONSE entry points forward to the maintained canonical runner.
- **B1/T-06 — Relevant input lineage:** Capability declarations now scope source kinds, profile sections and bound-period lookback. Runs persist that manifest; handlers receive only declared input kinds/sections. Receipt changes no longer invalidate journals, and journal documents do not invalidate cards. Accounting code lineage hashes core.py/modules.py and capability versions, excluding transport/CLI/UI. Invalidation remains conservative within each workflow/period population; per-item optimization/finalized packages are not claimed. Calendar-date period routing is explicit synthetic recurrence behavior; real client period/freshness rules remain Batch 2.
- **B1/T-07 — Governing artifacts and decisions:** Migration 5 links multiple runs to immutable artifacts. Envelopes cite dependency content hashes, not row IDs; byte-identical current preparations are reused. The newest completed linked preparation governs each workflow/period/item. State/export contain one item review state and all immutable links/history; non-governing decisions fail closed. Repeated decisions return 409; contradictory independent reviewers create disputed, never last-write-wins approval. Resolution is explicit resolve_approve/resolve_reject by a third non-contributing human reviewer in the synthetic service; real resolution authority remains unconfigured. Approved→revoke remains append-only.

Existing helpers and reviewer harness query membership rather than assume a new artifact row per execution. - **C-04 — Historical authorship:** Interim independence includes suppliers of all versions of every manifest input identity and all profile registrants, plus enqueuer, worker and mandate issuer. - **C-03 — Provenance separate from identity:** Migration 6 adds immutable artifact_contributors rows for every linked run. New content hashes exclude contributor identity; legacy envelopes/hashes remain byte-for-byte unchanged and their contributor lists remain authoritative. Review uses the union. - **C-01 — Locked-origin moves:** New source versions inspect prior admitted period lineage. - **T-12 — Ordered lifecycle:** Source envelopes accept explicit timestamp/sequence as_of, fixture system identity, tombstone/reason and supersession. Older/conflicting versions remain immutable history; heads retain the newer accepted version. Legacy fixture arrivals are labeled legacy_arrival and make no provider-order guarantee. Removals/supersession retain links and invalidate approved work visibly. Period opening/replay re-evaluates all quarantined source types; receipts follow their referenced transaction's period while keeping their own date for matching. Locked-origin protections remain enforced during re-binding.
- **T-10 — Standing authority:** Mandates are proposed until independently approved under an authority grant. They bind rule versions, explicit period selection and timestamp freshness predicates; changed policy requires reconfirmation, and stale/missing evidence leaves occurrences awaiting_evidence. Intake wakes such approved occurrences using the persisted simulation clock. Existing fixture recurrence tests now explicitly propose/approve calendar mandates with no required fresh kinds; new tests exercise required freshness and a fixed prior-period target. No real schedule or live execution is enabled.
- **T-13 — Statement completeness:** Explicit fictional statements now carry balances, signed totals by activity, line identities, counts, provenance and sign convention. Card work checks balance/activity ties, prior opening balance and population identity, with an unreconciled-population workpaper. Legacy count/total controls alone no longer confer eligibility. The synthetic fixture's payment sign is explicitly negative and historical snapshots are not rewritten. A test-only specification adapter upgrades original reviewer control fixtures, preserving deliberately wrong totals; runtime intake never derives a statement from transactions.
- **T-14 — Dispositions and dependency controls:** Migration 11 separates current exception status from immutable history and evidence/source-hash-bound human dispositions. Closed choices resolve demonstrated duplicate, credit, settlement, split and coding paths. A propose_rule disposition creates only a proposed rule. Explicit refer_external choices keep the underlying pending/currency/missing-document blocker and require acknowledged handover; no unsupported FX, receipt or recognition conclusion is invented. - **T-14 — Item lineage:** Historical suppliers are now computed from the item's own evidence and duplicate dependencies. A helper's unrelated receipt does not bar review of another item. Applied rule authors/approvers replace the interim all-profile-registrant rule. Relevant chart/entity/book/profile-component authors and approvers are also retained across cosmetic registrations, so configuration preparation cannot be laundered through another registrant. Provenance remains outside content identity.
- **T-15 — Proposed effects:** Card and journal preparation use one proposed-entry shape and shared mechanical validator. ## D-026 — Owner feed contract — 16 November 2026

**Scope.** Card transaction rows and their receipts in the fictional local feed. Journals are excluded. Whether a real provider behaves this way remains a gate G2 confirmation.

**What it promises.** For every delivery order the contract allows, one charge is never approved in a locked period and again in an open one, and nothing leaves a locked-period hold without a person's authority. It does not promise identical intermediate records in every order.

1. **Provider order.** Where messages carry a sequence number or timestamp, the highest one governs the row. An older or conflicting message is kept as evidence and never replaces the governing row.
2. **Claim on a late, older or conflicting message.** The replacement claim is still recorded for the row. If the row has no claim yet, the claim applies as if it had arrived in order. If the row already has the same claim, it is a repeat (clause 5). If the row has a different claim, it is a second claim (clause 7).
3. **Claim after its row.** A provider may declare "this replaces X" in a later message than the row. The claim is recorded once, the row is blocked at once, and any earlier approval stops governing.
4. **Claim before its target.** The row stays blocked as unresolved until X arrives, then links automatically. If the chain reaches a locked period, the row and its receipt are held under that period.
5. **Identical repeat.** Repeating a claim the row already has changes nothing about the row. A new batch keeps its own delivery record; an exact replay of a batch adds nothing.
6. **Later omission.** A later version that does not repeat a claim does not withdraw it.
7. **Second claim naming a different target.** This applies whether or not the first claim has linked yet. The second claim is recorded but not applied. The row gets a blocker that only a recorded, authorized disposition can clear, and any approval stops governing. The row stays where it is: not moved into a hold, not moved out of one. The second target is not retired. Further different claims join the same open question.
8. **Release from a locked-period hold.** A provider message alone never releases a charge held under a locked period. Release requires an authorized reopen of that period, or a recorded, authorized disposition.
9. **Who may disposition.** A disposition under clause 7 or 8 is recorded by someone with disposition authority who did not supply either message, states which target stands, and cites evidence. If it releases a charge from a locked period, that person must also hold the lock authority.

**Left open, outside this contract.** Whether a removed replacement restores the original (U4), and whether replacing an already withdrawn charge needs the closed period reopened (UC-14).

## D-048 — Owner decision: the agent keeps its records on a paid always-on service with a disk — 18 November 2026

The development service kept everything in memory: a restart, a deploy or the free tier's sleep lost every proposal, decision and posting record and dropped the QuickBooks sandbox connection, so nothing could run on a schedule. Fable put three ways forward to the owner on a card titled "Choose where the agent keeps its records so runs can be scheduled". On 18 November 2026 at 9:58 AM Eastern the owner chose:

> Paid always-on service with a disk

The card described that option as: "About $7 a month plus a small disk charge. Nothing is lost on restart, it never sleeps, and schedules can run. You make the upgrade in Render; I show the exact price first." The two options not chosen were a free database that expires after 30 days on a service that still sleeps, and leaving things as they were.

- **Price, read from Render's pricing page on 18 November 2026.** The smallest paid web service is $7 a month (512 MB, part of one CPU). A disk is $0.25 per GB a month, so $0.25 for 1 GB. The owner's workspace plan (Hobby) adds nothing. About $7.25 a month in all. Render's free-tier page says a free service sleeps after 15 minutes without traffic and cannot have a disk.
- **Who does what.** The owner makes the upgrade and adds the disk in Render, because it is a purchase. Fable then points the service at a file on that disk (the setting AGENT_DB, which is not a secret), deploys and checks that a restart loses nothing.
- **What was built.** With AGENT_DB naming a file, the service keeps its SQLite store there: clients, runs, proposals, decisions, standing approvals, postings and the audit chain. The QuickBooks sandbox connection is kept in the same file, saved when the owner connects and each time Intuit replaces the tokens, and taken up again at start without sending anything to Intuit. A kept connection that is incomplete never stops the service: it starts unconnected, says so in the audit chain, and the owner connects again from the page. Without AGENT_DB the service behaves as before, in memory.
- **The kept tokens.** The file holds the sandbox connection's sign-in tokens as plain text. The service sets the file readable by its own user only, and no page, API response or audit entry contains them. That is acceptable for a sandbox company in development and not for go-live: before any client's connection is kept, the tokens are to be encrypted or held in a secrets service. This is recorded as open work.
- **Review tests.** 114 in hosted_agent/tests/. Twelve deliberate faults in this change were each caught by at least one of them.
- **Not built or not proven.** The disk itself: nothing has been tried on Render yet, since the owner has not made the upgrade. A schedule. Encryption of the kept tokens. A copy of the file kept outside Render. The fictional companies' books are still in memory and start over at a restart while their records are kept. Render's page on disks, read the same day, says: a service with a disk runs as one instance and is unavailable for a few seconds at each deploy; only what is written under the disk's mount path is kept; a disk can be made larger later but not smaller; Render takes a snapshot of the disk every 24 hours and keeps it seven days.
- **What stays closed.** Client data, a client's live systems and any posting outside the sandbox (D-040). The service is still in the owner's personal Render workspace and moves to a separate one before any client data.
